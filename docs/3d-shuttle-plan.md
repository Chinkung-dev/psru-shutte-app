# แผนพัฒนาหมุดรถรับส่ง PSRU แบบโมเดล 3D จริง

วันที่จัดทำ: 2026-09-09
วันที่อัปเดตล่าสุด: 2026-09-10

อัปเดตส่งต่องาน 2026-09-11: ผู้ใช้พบโมเดลกับป้ายรถไม่ตรงกันขณะเลื่อนแผนที่ และโมเดลค้างหลังคนขับเปลี่ยนสถานะบน Web ยังไม่แก้สำเร็จ มี patch เตรียมจุดทดสอบใน `shuttle_3d_layer.dart` ที่ยังไม่ผ่านการตรวจหลังแก้ อ่าน [สถานะล่าสุดและแผนทำต่อ](3d-shuttle-handoff.md) ก่อนดำเนินงานต่อ ผลทดสอบที่บันทึกด้านล่างเป็นผลก่อน patch นี้

สถานะ: สร้างโมเดล GLB รุ่นแรกและเชื่อมโค้ดหน้านักศึกษาแล้ว; tests 3D 6 ข้อและ stop-five bypass 10 ข้อผ่าน ยังไม่ผ่านการตรวจรับครบทุกระยะ โดยเฉพาะการแสดงผลบนอุปกรณ์จริง ประสิทธิภาพ และ lifecycle

## 1. ผลลัพธ์ที่ต้องการและขอบเขต

เปลี่ยนหมุดรถในแผนที่ฝั่งนักศึกษาเป็นโมเดลสามมิติที่มี mesh และวัสดุจริง
หมุนตัวรถตามทิศทางการเคลื่อนที่ ขณะที่หมายเลขรถและสถานะยังอ่านตรงได้เสมอ
ใช้ flutter_map และระบบติดตามตำแหน่งเดิม ให้การเรียกรถ เส้นไฮไลท์ ETA และการเลือกป้ายทำงานต่อ

- เป้าหมายแรก: หน้านักศึกษาบน Android และ Flutter Web
- iOS: ต้องตรวจบนอุปกรณ์หรือสภาพแวดล้อม iOS ก่อนอ้างว่าผ่าน ไม่ใช้ผล Android แทน
- แอดมินและคนขับ: ออกแบบองค์ประกอบให้ใช้ร่วมกันได้ แต่แยกการนำไปใช้ในหน้าจอเหล่านี้เป็นระยะถัดไป
- แผนที่ยังเป็นแผนที่ 2D ตัวรถเป็นวัตถุ 3D ไม่รวมอาคาร 3D ภูมิประเทศ หรือแผนที่เอียงทั้งฉาก
- ภาพอ้างอิงมีมุมด้านหน้าและด้านข้าง จึงสร้างรูปทรงให้ใกล้เคียงได้ แต่ไม่อ้างว่าเป็นการสแกนรถหรือมีขนาดตรงของจริง

## 2. รูปลักษณ์โมเดลจากภาพอ้างอิง

| ส่วน | สิ่งที่จะสร้าง | ระดับรายละเอียด |
| --- | --- | --- |
| ตัวถัง | รถไฟฟ้ารับส่งสีขาว ทรงยาว ด้านข้างเปิด | เน้นสัดส่วนและทรงที่เห็นชัดเมื่อย่อบนแผนที่ |
| หลังคา | หลังคายาวสีขาว ขอบมน เสารองรับ | เป็น geometry จริง |
| ด้านหน้า | กระจกหน้าทรงโค้งขนาดใหญ่ กรอบสีเข้ม | ใช้วัสดุเข้มและเงาสะท้อนแบบเบา |
| ที่นั่ง | เบาะสีดำหลายแถวภายใน | ลดรายละเอียดส่วนที่มองไม่เห็นในขนาดหมุด |
| ทางขึ้นและราว | ช่องขึ้นด้านข้าง ราวจับและเสาขนาดเหมาะสม | รักษาเอกลักษณ์ด้านข้างเปิด |
| ล้อ | ยางดำ ดุมสีโลหะ แยกชิ้นส่วนไว้ | ยังไม่ทำระบบฟิสิกส์หรือช่วงล่าง |
| ตราสัญลักษณ์ | PSRU สีเขียวบริเวณหน้าและด้านข้าง พร้อมแถบสีเขียว | ใช้ texture จากสินทรัพย์ที่มีหรือจัดทำใหม่จากต้นแบบ |
| รายละเอียดเล็ก | กระจกข้าง ไฟหน้า กันชน ที่ปัดน้ำฝน | ใส่เท่าที่มีผลต่อการจำรูปรถ |
| ด้านหลัง | รูปทรงตามโครงรถและความสมมาตร | เป็นการประมาณ เพราะไม่มีภาพด้านหลัง |

ไม่ติดเลข 5 ถาวรบนโมเดล รถทุกคันใช้ geometry ร่วมกันและแสดงหมายเลขจากฐานข้อมูล
ไม่เปลี่ยนตัวถังทั้งคันเป็นสีแดงเมื่อเต็ม สีประจำรถยังคงเดิม ใช้ป้ายสถานะสื่อสารแทน

ไฟล์ส่งมอบโมเดล: GLB พร้อม texture ที่จำเป็น และไฟล์ต้นฉบับหรือสคริปต์สร้างที่แก้ไขต่อได้
สร้างด้วย Blender 5.2.1 LTS ที่ `C:/Program Files/Blender Foundation/Blender 5.2/blender.exe` ซึ่งไม่ได้อยู่ใน PATH; ดูคำสั่ง PowerShell ใน [คู่มือ setup](3d-shuttle-setup.md)

## 3. พิสูจน์การเรนเดอร์ก่อนทำรายละเอียดโมเดล

ใช้ three_js เป็นตัวเลือกแรกสำหรับทดสอบ ไม่ถือว่าการประกอบกับแอปผ่านแล้วเพียงเพราะ package ระบุรองรับแพลตฟอร์ม
เอกสารระบุใช้ ANGLE บนมือถือ/เดสก์ท็อป และ WebGL2 บนเว็บ จึงต้องตรวจทั้งข้อกำหนดเครื่องและการประกอบเลเยอร์

ขั้นทดลองทางเทคนิค:

1. วางวัตถุ 3D เรียบง่ายบนพื้นโปร่งใสเหนือแผนที่เดิม
2. ตรวจว่าผิวเรนเดอร์โปร่งใสจริง ไม่มีพื้นดำหรือกล่องทึบบังแผนที่
3. ลาก ซูม หมุน และเปลี่ยนขนาดหน้าจอ โดยจุดยึดรถยังตรงกับตำแหน่งแผนที่
4. ทดสอบว่า gesture ไปถึงแผนที่ และการแตะเลือกป้าย/รถยังทำงาน
5. ทดสอบหลายวัตถุใน scene เดียว เพื่อตรวจต้นทุนก่อนเพิ่มโมเดลเต็ม
6. ทดสอบ Android และ Web ด้วย build ที่ใกล้เคียงการใช้งานจริง

เกณฑ์ผ่าน: โหลด renderer ได้ วัตถุไม่หลุดพิกัด พื้นโปร่งใส gesture ปกติ และไม่มีปัญหา lifecycle เมื่อออก/กลับเข้าหน้า
หากไม่ผ่าน จะทบทวนตัว renderer หรือวิธีประกอบเลเยอร์ก่อนขยายงาน ไม่เปลี่ยนผลส่งมอบเป็นภาพ 2D โดยเรียกว่าสำเร็จ

อ้างอิง:
- [three_js](https://pub.dev/packages/three_js)
- [flutter_angle](https://pub.dev/packages/flutter_angle)
- [flutter_map Marker Layer](https://docs.fleaflet.dev/layers/marker-layer)

## 4. การวางชั้นแผนที่และรถ

ใช้ scene 3D ร่วมกันหนึ่งชุดต่อหน้าแผนที่ โหลดโมเดลหนึ่งครั้งแล้วสร้าง instance ของรถแต่ละคัน
หลีกเลี่ยง renderer หรือ WebView แยกต่อรถหนึ่งคัน

ลำดับองค์ประกอบที่เสนอ:

1. แผนที่และเส้นทางของ flutter_map
2. โมเดลรถในชั้น 3D โปร่งใส
3. หมายเลขรถ ป้ายสถานะ และพื้นที่รับการแตะใน Flutter
4. ป้ายที่เลือก ข้อความ ETA และแผงการเดินทางที่ต้องอยู่ด้านหน้า

จัดลำดับกับหมุดป้ายเดิมอย่างชัดเจน ไม่ให้ชั้นรถบังป้ายปลายทางหรือปุ่มเรียกรถ
ชั้นเรนเดอร์ไม่รับ gesture หมุนโมเดลจากนิ้วโดยตรง; การหมุนบนแผนที่มาจากข้อมูลรถ
หากต้องการดูโมเดลแบบหมุนอิสระ ให้ใช้หน้าพรีวิวแยก

ใช้ตำแหน่งแผนที่ที่ผ่าน animation เดิมเป็นแหล่งข้อมูลร่วมของโมเดลและป้ายกำกับ
แปลงพิกัดผ่านกล้องของ flutter_map ไปยังพิกัดหน้าจอ แล้วแปลงเข้าฉาก 3D
ใช้กล้อง orthographic เป็นตัวเลือกแรก เพื่อควบคุมจุดยึดและขนาดบนหน้าจอได้ง่าย
มุมมองรถจะเป็นมุมสูงที่ยังเห็นด้านข้าง โดยต้องตรวจทิศหัวรถหลังฉายภาพในหลายมุม

จุดยึดอยู่กึ่งกลางฐานรถ ไม่ใช่ยอดหลังคาหรือกึ่งกลางภาพ
เมื่อหมุนแผนที่ ต้องปรับการฉายทิศรถด้วย โดยทิศทางทางภูมิศาสตร์ของรถยังคงเดิม

## 5. ทิศทางรถและ animation

เริ่มจากคำนวณ bearing ด้วย GPS สองตำแหน่งที่เชื่อถือได้ในข้อมูลรถเดิม
ยังไม่เพิ่มการเขียนฐานข้อมูลหรือ stream ใหม่เพียงเพื่อหมุนโมเดล

ขั้นตอนประมวลผล:

1. รับตำแหน่งใหม่ของรถแต่ละคัน พร้อมข้อมูลเวลาที่มีอยู่
2. ปฏิเสธตำแหน่งไม่ถูกต้อง ข้อมูลเก่า และการกระโดดที่ไม่สมเหตุสมผล
3. ใช้การเคลื่อนที่สะสมที่มากพอก่อนคำนวณทิศ เพื่อลดความไวต่อ GPS noise
4. คำนวณ bearing ในพิกัดโลก แล้วทำ smoothing แยกตามรถ
5. หมุนผ่านมุมที่สั้นที่สุด เช่น 359° ไป 1° หมุนเพียง 2°
6. ใช้ timeline เดียวกับตำแหน่งรถที่เคลื่อนบนแผนที่ เพื่อไม่ให้หัวรถกับตัวรถกระตุกคนละจังหวะ
7. เมื่อรถหยุดหรือมี heartbeat ที่ตำแหน่งเดิม ให้คงทิศล่าสุด
8. เมื่อยังไม่มีข้อมูลทิศเพียงพอ ใช้มุมเริ่มต้นคงที่จนมีหลักฐานการเคลื่อนที่ ไม่อ้างว่าเป็นทิศจริง
9. เมื่อรถหาย/เปลี่ยนคัน ล้าง state ที่ไม่เกี่ยวข้อง และจัดการข้อมูลเก่าก่อนกลับมาแสดง

ค่าเริ่มต้นสำหรับทดลอง: ระยะสะสมประมาณ 3–5 เมตร และการหมุนต่อเนื่องประมาณ 200–500 ms
ต้องปรับจากการทดสอบจริง ไม่ใช้ตัวเลขนี้เป็นข้อรับประกันความแม่นยำ
ไม่ใช้ลำดับป้ายหรือเส้นไฮไลท์เป็นหลักฐานทิศรถ เพราะอาจไม่ตรงกับทางที่รถเลือก เช่นกรณีข้ามป้าย 5

## 6. หมายเลขรถ สถานะ และการอ่านบนแผนที่

แยกป้ายกำกับออกจากโมเดล ใช้ Flutter text ที่อ่านตรงเสมอ ไม่หมุนตามตัวรถ

| ข้อมูล | การแสดงผลที่เสนอ |
| --- | --- |
| หมายเลข | ป้ายพื้นเข้ม ข้อความขาว เช่น 01 หรือ 05 ดึงจากข้อมูลจริง |
| ว่าง | จุดสีเขียวและข้อความ “ว่าง” |
| เต็ม | จุดสีเทาเข้มหรือแดงและข้อความ “เต็ม”; เลือกสีสุดท้ายให้สอดคล้องกับ UI เดิม |
| พัก | จุดสีส้มและข้อความ “พัก” |
| รถเป้าหมาย | เส้นขอบหรือวงเน้นที่ฐาน และป้ายที่เด่นกว่ารถอื่น |
| ไม่ทราบสถานะ | แสดงว่าไม่ทราบ ไม่ตีความว่าเป็นรถว่าง |
| Offline/ข้อมูลหมดอายุ | ทำตามนโยบายการแสดงรถเดิมของหน้า ไม่แสดงเป็นรถพร้อมให้บริการ |

เริ่มทดสอบตัวรถราว 48–64 logical pixels และพื้นที่แตะอย่างน้อย 44 logical pixels
ปรับขนาดตาม zoom ภายในขอบเขต ไม่ให้ย่อจนอ่านหมายเลขไม่ได้หรือขยายจนบังแผนที่
ไม่อาศัยสีอย่างเดียวในการบอกสถานะ ต้องมีข้อความหรือ semantic label ด้วย
การซ้อนกันของรถหลายคันต้องทดสอบ และให้รถที่กำลังติดตามมีลำดับความสำคัญในการแสดงป้าย

## 7. งบประสิทธิภาพและการจัดการทรัพยากร

ตัวเลขต่อไปนี้เป็นเป้าหมายเริ่มต้น ต้องวัดบนอุปกรณ์จริงก่อนยืนยัน:

- โมเดลประมาณ 8,000–15,000 triangles และ GLB รวม texture เป้าหมายไม่เกิน 2 MB
- ใช้ texture หลักประมาณ 1024 px และลดจำนวนวัสดุ/การสลับ draw call
- ใช้แสงเรียบง่ายและเงาสัมผัสแบบเบา งดเอฟเฟกต์สะท้อนหรือเงาแพงในรุ่นแรก
- แชร์ geometry และ material ระหว่างรถ; แต่ละคันเก็บเฉพาะตำแหน่ง ทิศ และ state ของตนเอง
- โหลดจาก assets ของแอปและเก็บในหน่วยความจำระหว่างใช้หน้า ไม่โหลด GLB ใหม่ทุก GPS update
- อัปเดต scene เมื่อกล้อง รถ สถานะ หรือ animation เปลี่ยน ไม่สร้าง scene ใหม่ทุก Flutter build
- หยุด animation เมื่อหน้าไม่แสดงหรือแอปอยู่เบื้องหลัง และ dispose ทรัพยากรเมื่อออกจากหน้า
- ทดสอบรถ 1, 5 และ 10 คัน ตั้งเป้าอย่างน้อย 30 FPS บน Android ระดับกลางที่ใช้ทดสอบ
- วัดจาก profile/release build ไม่ใช้ตัวเลข debug build ตัดสิน

ระหว่างโมเดลโหลด หรือเมื่ออุปกรณ์เปิด renderer ไม่ได้ ให้แสดงหมุดเดิมเพื่อให้ติดตามรถได้ต่อ
กรณีนี้เป็น fallback ที่ต้องระบุและทดสอบ ไม่ใช่ผลสำเร็จของการเรนเดอร์ 3D
จะมีสวิตช์เปิด/ปิดฟีเจอร์สำหรับทดสอบและย้อนกลับได้โดยไม่แก้ระบบเรียกรถ

## 10. รายการตรวจรับ

- เป็นโมเดลสามมิติจริง หมุนแล้วเห็นด้านที่ต่างกัน ไม่ใช่ภาพแบนที่หมุนในระนาบ
- รูปลักษณ์ขาว–เขียว กระจกหน้ากว้าง หลังคายาว ด้านข้างเปิด และเบาะดำสอดคล้องกับภาพอ้างอิง
- แสดงได้เมื่อไม่มีรถ มีรถหนึ่งคัน และหลายคัน โดยแยกทิศกับสถานะต่อคัน
- หัวรถสัมพันธ์กับทิศการเคลื่อนที่จริง และไม่หมุนวนยาวเมื่อข้าม 0°
- รถหยุดหรือได้รับตำแหน่งซ้ำแล้วไม่หมุนสั่น
- ลาก ซูม หมุนแผนที่ และปรับหน้าจอแล้วจุดฐานรถกับหมุดพิกัดไม่เลื่อนแยกกัน
- หมายเลขและข้อความสถานะอ่านตรงได้ทุกทิศ ไม่ถูกตัวรถบัง
- รถที่เลือกยังเด่น การแตะป้ายและการใช้งานแผนที่ไม่ถูกชั้น 3D ขวาง
- การเรียกรถ เส้นไฮไลท์ ETA การกู้คืนคำขอ และกรณีข้ามป้าย 5 ยังทำงานตามเดิม
- โมเดลโหลดไม่สำเร็จ renderer ใช้ไม่ได้ และ GPU context หายแล้วแอปยังใช้งานต่อได้
- ทดสอบออก/เข้าหน้าและ background/resume ซ้ำโดยไม่เกิด renderer หรือ listener ค้าง
- บันทึกเครื่องที่ใช้ทดสอบ build mode จำนวนรถ และผลประสิทธิภาพจริง

## 11. ข้อจำกัดและการตัดสินใจที่ยึดไว้ในแผน

ภาพเดียวเพียงพอสำหรับสร้างโมเดลเพื่อใช้เป็นหมุด แต่ไม่เพียงพอสำหรับความแม่นยำเชิงวิศวกรรม
ด้านหลังและสัดส่วนบางส่วนจะประมาณและแสดงให้ตรวจในหน้าพรีวิว
รายละเอียดการตกแต่งเล็กมากจะลดลงเมื่อไม่ช่วยให้เห็นรถบนแผนที่ชัดขึ้น
การเรนเดอร์หลายแพลตฟอร์มและความแม่นยำ GPS ต้องพิสูจน์จากการทดสอบ ไม่รับประกันจากเอกสาร package อย่างเดียว

   - **การแก้ไขปัญหา ABI Mismatch (Linker Crash):**
     - ไลบรารีกราฟิก `flutter_angle` บรรจุไฟล์ไบนารีเนทีฟ `.so` เฉพาะ `arm64-v8a` บน Android
     - หากใน APK มีโฟลเดอร์ `lib/x86_64/` ติดมาจาก dependency อื่น (`dartjni`, `datastore_shared_counter`) ระบบปฏิบัติการ Android บน Emulator x86_64 จะเลือกบูตด้วย Zygote 64-bit x86_64 ส่งผลให้เกิดข้อผิดพลาด `java.lang.UnsatisfiedLinkError: libflutter.so is for EM_AARCH64 instead of EM_X86_64` ขณะเริ่มต้นแอป
     - ทำการกำหนด `ndk.abiFilters += listOf("arm64-v8a")` และเพิ่ม `packaging.jniLibs.excludes += listOf("lib/x86_64/**", "lib/armeabi-v7a/**", "lib/x86/**")` ใน `android/app/build.gradle.kts` ส่งผลให้แอปถูกแพ็กเกจเป็น ARM64 แบบเอกภาพ และรันผ่านกลไก ARM Translation ของ Emulator ได้อย่างราบรื่น

   - **สาเหตุเชิงลึก:**
     1. ในเฟรมแรกสุดของการเรนเดอร์ วิดเจ็ต `FlutterMap` ยังไม่เสร็จสิ้นขั้นตอน Layout ทำให้ค่า `mapCamera.nonRotatedSize` มีขนาดเป็น `Size(0.0, 0.0)`
     2. `Shuttle3DLayer` ส่งค่าขนาด 0x0 เข้าสู่ `_GuardedThreeJS` ส่งผลให้ `FlutterAngle.createTexture` ถูกเรียกด้วยขนาดกว้าง 0 และสูง 0
     3. ปลั๊กอินแอนดรอยด์ตอบกลับด้วย `PlatformException(no texture width, no texture width, 0, null)`
     4. ฟังก์ชัน `_fail()` ทำการดักจับข้อผิดพลาดและสั่ง `_engine.dispose()` ซึ่งไปเรียก `_libEGL!.dispose()` ทำให้ตัวแปรแบบคงที่ (Static) `LibEGL? _libEGL` ถูกล้างค่าเป็น `null`
     5. เมื่อเฟรมถัดไปของหน้าจอจัดขนาดเสร็จ (`616x1219`) หรือ Ticker ของแอนิเมชันเริ่มทำงาน การเรียก `FlutterAngle.activateTexture` จึงพยายามใช้ `_libEGL!.eglMakeCurrent` ซึ่งเกิด Null check crash ซ้ำซ้อน
   - **การแก้ไข:**
     1. ปรับ `Shuttle3DLayer.build` ให้ตรวจสอบ `size.width <= 1 || size.height <= 1` หากขนาดยังไม่พร้อม ให้ส่งคืน `const SizedBox.shrink()` เพื่อรอจนกว่าแผนที่จะจัดขนาดเสร็จสมบูรณ์
     2. ใน `_GuardedThreeJS.initPlatformState` เพิ่มการตรวจสอบขนาดก่อนส่งคำสั่งสร้าง Texture
     3. ใน `customRenderer` เพิ่มการตรวจสอบสถานะ `!_engine.isClosed` เพื่อป้องกันการวาดหลังถูกยกเลิก

### บันทึกการปฏิรูปสถาปัตยกรรมข้อมูลสู่ Realtime Database (Single Source of Truth) วันที่ 2026-09-10

สืบเนื่องจากปัญหาความซ้ำซ้อนและการไม่ซิงก์กันของข้อมูลรถและสถานะคนขับระหว่าง Cloud Firestore (คอลเล็กชัน `shuttles`) และ Firebase Realtime Database (โหนด `shuttles`) ทีมพัฒนาจึงได้ทำการปรับโครงสร้างข้อมูลทั้งหมดให้ Firebase Realtime Database (RTDB) ทำหน้าที่เป็น **Single Source of Truth** แต่เพียงผู้เดียวสำหรับข้อมูลรถรับส่งและคนขับ โดยมีรายละเอียดเชิงลึกดังนี้:

#### 1. การแบ่งขอบเขตหน้าที่ของฐานข้อมูล (Database Responsibility Segregation)
- **Firebase Realtime Database (RTDB):**
  - จัดเก็บข้อมูลรถรับส่งทั้งหมด (`shuttles/shuttle_01` ถึง `shuttles/shuttle_05`)
  - จัดเก็บพิกัด GPS สด (`lat`, `lng`), ความเร็ว, ทิศทาง (Bearing)
  - จัดเก็บสถานะการให้บริการ (`status`: `online`/`offline`, `passenger_status`: `available`/`full`/`break`/`offline`)
  - จัดเก็บข้อมูลการผูกคนขับกับรถ (`driver_uid`, `driver_name`, `driver_avatar`)
  - จัดเก็บตารางตรวจสอบสิทธิ์ความเป็นเจ้าของรถ (`shuttle_drivers/{shuttleKey}`)
- **Cloud Firestore:**
  - จัดเก็บบัญชีผู้ใช้งานและสิทธิ์ (`users/{uid}`: role `student`, `driver`, `admin`)
  - จัดเก็บข้อมูลจุดจอดรถประจำทาง (`stops`)
  - จัดเก็บประวัติและคำขอเรียกรถ (`ride_requests`)
  - จัดเก็บข้อความสนทนาระหว่างผู้โดยสารและคนขับ (`chats`)
  - **ยกเลิกและทำความสะอาด:** คอลเล็กชัน `shuttles` ใน Firestore ถูกเลิกใช้งานและมีคำสั่งทำความสะอาดอัตโนมัติ

#### 2. การสร้างและจัดการข้อมูลรถ 5 คันใน RTDB (`lib/services/shuttle_access.dart`)
- **มาตรฐานชื่อและหมายเลขรถ:**
  - ชื่อรถ: `shuttle#01`, `shuttle#02`, `shuttle#03`, `shuttle#04`, `shuttle#05`
  - หมายเลขรถ: `SH#01`, `SH#02`, `SH#03`, `SH#04`, `SH#05`
  - คีย์ในฐานข้อมูล: `shuttle_01`, `shuttle_02`, `shuttle_03`, `shuttle_04`, `shuttle_05`
- **ฟังก์ชันสำคัญที่เพิ่มขึ้นและปรับปรุง:**
  - `ensureDefaultShuttles([int targetCount = 5])`: ตรวจสอบและสร้างโหนดรถทั้ง 5 คันใน RTDB พร้อมเรียก `cleanLegacyFirestoreShuttles()` เพื่อลบเอกสารตกค้างใน Firestore
  - `getAvailableShuttles({String? currentDriverUid})`: คืนค่ารายการรถที่ยังไม่มีคนขับ (`driver_uid == null`) หรือเป็นรถที่คนขับปัจจุบันกำลังผูกอยู่ เรียงลำดับตามหมายเลขรถอย่างถูกต้อง
  - `assignDriver(...)`: ผูกคนขับเข้ากับรถในโหนด `shuttles` และ `shuttle_drivers` ใน RTDB
  - `unassignShuttleByName(String name)` / `unassignShuttleByKey(String key)`: ปลดคนขับออกจากรถใน RTDB เมื่อมีการสลับหรือลบคนขับ
  - `shuttleDatabaseKey(...)`: แปลงชื่อและหมายเลขรถให้เป็นคีย์มาตรฐาน `shuttle_01` ถึง `shuttle_05` อย่างแม่นยำ

3. บันทึกข้อมูลส่วนตัว (ชื่อ, เบอร์โทร, รหัสพนักงาน, รูปโปรไฟล์) ลงในคอลเล็กชัน `users` ของ Firestore เป็นหลักก่อน

### REV-02 — Cleanup ลบข้อมูลเดิมก่อนตรวจสอบการย้ายข้อมูล [P1 / Spec]

**ตำแหน่ง:** `lib/services/shuttle_access.dart`

**เงื่อนไขและผลกระทบ:** รถมีคนขับใน Firestore แต่ยังไม่มีโหนดรถใน RTDB เมื่อเปิดหน้าแอดมินหรือเตรียมรายการรถ ระบบสร้างโหนดใหม่โดยไม่มี `driver_uid` แล้วเรียกลบเอกสารรถเดิมทั้งหมด รายการเลือกรถจึงอาจมองว่ารถว่าง ทั้งที่ `shuttle_drivers` ยังผูกเจ้าของเดิมอยู่ ข้อมูลรถเดิมถูกลบก่อนตรวจสอบ แม้ข้อมูลบางส่วนอาจยังอยู่ใน `users` หรือ mapping อื่น

**วิธีแก้ที่ดำเนินการแล้ว:**
1. นำการเรียก `cleanLegacyFirestoreShuttles()` ออกจาก `ensureDefaultShuttles()` และหน้าจอแอดมิน เพื่อไม่ให้การเปิดหน้าหรือโหลด dropdown ลบข้อมูลใน Firestore โดยอัตโนมัติ
2. ใน `ensureDefaultShuttles()`: ตรวจสอบข้อมูลใน `shuttle_drivers` ก่อนสร้างโหนดเริ่มต้น หากมีคนขับผูกอยู่เดิมจะรักษา UID นั้นไว้ ไม่เซ็ตเป็น null
3. สร้างระบบ Migration ปลอดภัย `migrateFirestoreShuttlesToRtdb()`:
   - ตรวจจับความขัดแย้งของคนขับ (Conflict Detection) ระหว่าง Firestore กับ RTDB หากไม่ตรงกันจะบันทึกใน `conflictedShuttles` และคงข้อมูลต้นทางไว้ ไม่เขียนทับ
   - รักษาพิกัดและสถานะสดใน RTDB (`lat`, `lng`, `status`, `passenger_status`)
   - ใช้วิธี Optimistic Concurrency Check ตรวจสอบ `shuttle_drivers` ก่อนทำการอัปเดตแบบ Atomic ป้องกันข้อมูลถูกเปลี่ยนระหว่างทาง
4. สร้างระบบ Verified Pre-cleanup `cleanMigratedFirestoreShuttles({required report})`:
   - ตรวจสอบข้อมูลล่าสุดใน Firestore และ RTDB ซ้ำอีกครั้งก่อนลบ
   - หากข้อมูลใน Firestore ถูกแก้ไขหลังจัดทำรายงาน หรือข้อมูลใน RTDB ไม่ตรงกับที่ยืนยัน จะข้ามการลบและรายงานข้อขัดแย้งทันที

**สถานะ:** แก้โค้ดแล้ว
**การทดสอบและผลจริง:**
- Unit Test ใน `test/review_fixes_test.dart` ผ่าน: ทดสอบโครงสร้างรายงาน `ShuttleMigrationReport`, การตรวจจับความขัดแย้งคนขับ, และการข้ามการลบเมื่อข้อมูลถูกแก้ไขหลังออกรายงาน
**สิ่งที่ต้องทดสอบยืนยันต่อ:** รันจำลอง Migration บน Firebase Emulator Suite เพื่อยืนยัน Atomic multi-path update ข้ามแหล่งข้อมูล

### REV-03 — รถเริ่มงานแล้วยังแสดงสถานะผู้โดยสารออฟไลน์ [P2 / Spec]

**ตำแหน่ง:** `lib/screens/driver/driver_home.dart`

**เงื่อนไขและผลกระทบ:** รถที่สร้างใหม่หรือถูกปลดแล้วมอบหมายใหม่มี `passenger_status: offline` เมื่อคนขับเริ่มงาน โค้ดเปลี่ยนเพียง `status: online` ทำให้รถออนไลน์บนแผนที่ แต่ป้ายสถานะยังแสดงออฟไลน์จนกว่าจะเปลี่ยนสถานะเอง

**วิธีแก้ที่ดำเนินการแล้ว:**
1. รวมการอัปเดตสถานะเริ่มงานไว้ในเมธอดเดียว `_updateShiftStartStatus(LatLng loc)`
2. ตรวจสอบและแปลงค่า `passenger_status`: หากเป็น `'offline'`, ค่าว่าง หรือค่าที่ไม่ถูกต้อง ให้เปลี่ยนเป็น `'available'` โดยอัตโนมัติ; หากเป็นค่าที่ใช้งานได้อยู่แล้ว (`'available'`, `'full'`, `'break'`) ให้รักษาค่านั้นไว้
3. ส่งคำสั่งอัปเดต `status: 'online'`, `passenger_status`, พิกัด GPS, และ `last_updated` พร้อมกันในคำสั่งเดียว ทั้งในเส้นทาง GPS ปกติและเส้นทาง Fallback
4. จัดการ try-catch พร้อมแจ้งเตือน `TopToast` แสดงข้อผิดพลาดให้คนขับทราบอย่างชัดเจนหากบันทึกไม่สำเร็จ

### REV-05 — Startup timeout ทำงานระหว่างพัก renderer [P2 / Standards]

**ตำแหน่ง:** `lib/widgets/shuttle_3d_layer.dart`

**เงื่อนไขและผลกระทบ:** เปิด 3D แล้วสลับแท็บหรือพักแอปก่อนเฟรมแรก renderer หยุดตาม `visible`/`TickerMode` แต่ timer 20 วินาทียังเดินและเรียก `_fail` เมื่อกลับมาจึงเหลือหมุดสำรองจนกว่าจะเปิด 3D ใหม่

**วิธีแก้ที่ดำเนินการแล้ว:**
1. ปรับปรุงระบบนับเวลาด้วย Pausable Startup Budget Timer (`_remainingStartupBudget = 20s` ร่วมกับ `Stopwatch`)
2. นับเวลาถอยหลังเฉพาะเมื่อหน้าจอทำงานจริง (`_foreground && TickerMode.valuesOf(context).enabled`)
3. ใน `didChangeDependencies` และ `didChangeAppLifecycleState`: เมื่อแอปถูกพัก สลับแท็บ หรือ TickerMode ถูกปิด จะสั่งหยุด Timer และหักลบเวลาที่ผ่านไปออกจาก `_remainingStartupBudget`
4. เมื่อแอปกลับมาทำงาน จะนับต่อจากเวลาคงเหลือโดยไม่รีเซ็ตงบเวลาใหม่
5. สั่งยกเลิก Timer ทันทีเมื่อเฟรมแรกพร้อมแสดงผล (`_ready = true`), เกิดความล้มเหลวจริง (`_fail`), หรือเมื่อ `dispose()`

**สถานะ:** แก้โค้ดแล้ว (ผ่าน Unit Test)
**การทดสอบและผลจริง:**
- Unit Test ใน `test/review_fixes_test.dart` ผ่าน: ตรวจสอบตรรกะการหยุดนับเวลาขณะพักแอป และนับต่อจากงบเวลาคงเหลือได้อย่างถูกต้อง

### REV-06 — Renderer เก่า dispose หลัง renderer ใหม่เริ่มทำงาน [P2 / Standards]

**ตำแหน่ง:** `lib/widgets/shuttle_3d_layer.dart`

**เงื่อนไขและผลกระทบ:** เปลี่ยนขนาดแผนที่หรือปิด–เปิด 3D ขณะเริ่มต้นช้า ตัวใหม่อาจเริ่มก่อนตัวเก่าโหลดเสร็จ จากนั้นตัวเก่าจึงเรียก dispose ซึ่งแพ็กเกจ `flutter_angle` ที่ใช้อยู่ล้างตัวอ้างอิง EGL แบบ static ส่งผลให้ตัวใหม่มีโอกาสเรนเดอร์ล้มเหลว

**วิธีแก้ที่ดำเนินการแล้ว:**
1. พัฒนา `RendererLifecycleCoordinator`: ตัวประสานระดับ Static สำหรับจัดคิวการทำงานของ Renderer ข้ามทุก instance
2. กำหนดให้กระบวนการ `initPlatformState()` และ `dispose()` ของทุกตัวรันผ่าน `RendererLifecycleCoordinator.schedule(...)` เพื่อรับประกันการทำงานแบบ Sequential: Renderer ตัวใหม่จะไม่เริ่ม initialization จนกว่า teardown และ dispose ของตัวเก่าจะเสร็จสมบูรณ์ 100%
3. เพิ่ม Generation Token ให้แต่ละ instance: ป้องกัน callback, animation loop, และ GLB Loader เก่ากลับมาแก้ไขสถานะหรือแสดงผลข้ามรุ่น

**สถานะ:** แก้โค้ดแล้ว (รอทดสอบยืนยันบน Android)
**การทดสอบและผลจริง:**
- Unit Test ใน `test/review_fixes_test.dart` ผ่าน: ยืนยันว่างาน teardown ของ Task 1 เสร็จสิ้นก่อน Task 2 เริ่มทำงาน และ Generation Token เพิ่มขึ้นตามลำดับอย่างแม่นยำ
**สิ่งที่ต้องทดสอบยืนยันต่อ:** ทดสอบบน Android Emulator และอุปกรณ์จริง เพื่อยืนยันว่าการหมุนจอ พับจอ หรือเปิด-ปิด 3D ซ้ำๆ ไม่ทำให้ EGL context เกิดข้อผิดพลาด
